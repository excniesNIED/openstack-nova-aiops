# 合并版 AIOps 系统设计方案（简化版）

**项目主题一句话定义**：  
基于 OpenStack Nova 日志的实时 AIOps 系统，支持日志流式接入、模板化解析、窗口聚合、异常检测与故障分类、告警生成、LLM 智能解释与排障建议，以及可视化运维看板。

本方案融合了方案1的工程深度（窗口聚合、模板化、完整数据流、看板设计）和方案2的简洁亮点（小模型快速过滤 + 大模型精准分析的协同架构、易实现闭环），同时去除复杂部分（如 RAG、HBase 多层存储、Hive 分层、模型版本切换、多实体分组窗口），大幅降低实现难度，确保“能做完、能讲清楚、能加分”。

核心简化原则：
- 存储统一用 MariaDB/SQLite（告警 + 统计），原始日志可选存本地/HDFS。
- 模板化用简单正则实现（不去实现完整 Drain）。
- 窗口为全局固定 60s（不按 instance_id 分组）。
- LLM 只在告警触发时调用，prompt 固定、无 RAG。
- 模型主线为监督分类（normal + 3 类故障），输出分类概率触发告警。
- 强调“小模型（ML）在流式层毫秒级过滤 99% 正常日志，大模型（LLM）只处理异常窗口进行深度解释”的架构亮点。

---

## 1. 最终交付产物清单（报告/PPT 必写）

1. **数据管道**：Kafka + Spark Structured Streaming
2. **模型训练与评估**：Scikit-learn（RandomForest/XGBoost）
3. **在线推理与告警服务**：FastAPI + MariaDB/SQLite
4. **LLM 运维助手**：结构化解释与排障建议
5. **前端看板**：Vue + Astro + Charts
6. **一键运行环境**：Docker Compose（Kafka + Spark + FastAPI + Frontend + MariaDB）

---

## 2. 功能与非功能需求（最低标准）

### 功能需求（必须实现）
- 支持数据集切换：normal / fault1 / fault2 / fault3 / sample（回放源）
- 实时回放 sample.log，带速率控制（模拟线上）
- 日志解析：抽取时间、级别、组件、instance_id/request_id（可选）、消息正文
- 简单模板化：正则替换 UUID/IP/数字为占位符，生成 template_id
- 60s 全局滑动窗口聚合：模板计数向量、ERROR 比例、Top 模板
- 在线推理：输出 predicted_fault_type + probability
- 告警触发：非 normal 概率 > 阈值（e.g., 0.7），落库 + 推前端
- 告警详情：窗口统计 + 关键日志片段 + LLM 结构化建议

### 非功能需求（加分项）
- 吞吐：支持 100–300 lines/s 回放不滞后
- 延迟：日志进入 Kafka → 前端告警 < 5 秒
- 可复现：Docker 一键启动 + 固定随机种子

---

## 3. 总体架构（文字版，可直接画图）

```
(A) 数据接入层
Log Replayer (Python 脚本读取 sample.log) → Kafka topic: openstack.raw

(B) 流式处理层 (Spark Structured Streaming)
消费 openstack.raw →
  - 简单解析 + 模板化
  - 60s 全局窗口聚合 → 特征向量 (模板计数 + ERROR 比例)
  - 输出 Kafka topic: openstack.features

(C) 推理与告警层 (FastAPI)
消费 openstack.features →
  - 加载 ML 模型 → 预测 fault_type + prob
  - 若异常 → 生成告警 → 存 MariaDB
  - 异步调用 LLM 生成解释
  - 通过 WebSocket / SSE 推送告警到前端

(D) 可视化层 (Vue + Astro)
实时展示告警列表、趋势图、Top 模板、告警详情（含 LLM 建议）
```

## 4. 数据与 Topic 设计（简化版）

### Kafka Topic（2 个即可）
1. `openstack.raw`：每条消息 = 一行原始日志（value: {"ts": ..., "raw": "..."}）
2. `openstack.features`：窗口特征（value: {"window_start": ..., "template_counts": {...}, "error_ratio": ..., "top_templates": [...]}）

### 存储（MariaDB/SQLite 主库）
- `alerts` 表：alert_id, timestamp, window_start/end, pred_class, probability, severity, status
- `alert_details` 表：alert_id, template_stats (JSON), key_logs (JSON 数组，存窗口内 ERROR 日志), llm_summary, llm_steps
- 原始日志可选本地文件或不持久化（回放用完即丢）

---

## 5. 日志解析与模板化（简化实现）

- 核心字段：event_ts, level, component, instance_id (若有), raw_message
- 模板化：用几条正则替换常见变量（UUID、IP、数字、路径），生成 normalized_message → hash 为 template_id
- 报告中强调：模板化减少噪声，提升模型泛化与可解释性（Top 模板即“症状”）

---

## 6. 特征工程与模型（主线：监督分类）

- 标签：normal (0) / fault1 / fault2 / fault3
- 窗口特征：
  - Bag-of-Templates 计数向量（用 sklearn CountVectorizer，固定 vocab 从训练集学）
  - ERROR/WARN 比例
  - Top 10 模板 ID 及计数
- 模型：Scikit-learn RandomForest 或 XGBoost（易训练、解释好）
- 告警触发：pred_class != normal 且 prob > 0.7，或 normal_prob < 0.5

亮点：ML 模型在 Spark 中实时处理所有窗口（轻量、快速），只把异常窗口送 LLM 深度分析 → 成本性能权衡。

---

## 7. 训练流程（离线）

1. 用 Spark 或本地 Python 批处理 4 个训练日志文件 → 解析 + 模板化 + 窗口聚合 → 生成特征数据集 (Parquet/CSV)
2. Python (sklearn) 训练模型 + 保存 model.pkl + vectorizer.pkl
3. 离线评估：Accuracy、Macro-F1、Confusion Matrix

---

## 8. 在线推理与告警（FastAPI）

- 后台 Worker：消费 openstack.features → 推理 → 若告警 → 存 DB + 异步调用 LLM + 推送前端
- API：
  - POST /replay/start (dataset, rate)
  - GET /alerts (列表 + 过滤)
  - GET /alerts/{id} (详情，含 LLM 输出)

---

## 9. LLM 运维助手（简化、无 RAG）

- 只在告警生成后异步调用
- Prompt 模板（固定、强约束）：
```
你是一名资深 OpenStack 运维专家。
检测到故障类型：{pred_class} (置信度 {prob:.2f})
窗口统计：ERROR比例 {error_ratio:.2f}，Top模板：{top_templates}
关键日志片段：
{key_logs}

请结构化输出 JSON：
{
  "summary": "一句话总结问题",
  "suspected_causes": ["原因1", "原因2"],
  "next_steps": ["步骤1: 命令或检查点", "步骤2: ..."],
  "impact": "可能影响描述"
}
```
- 输出强制 JSON，前端直接渲染

---

## 10. 前端看板（4 页核心）

1. **Overview**：回放状态、告警趋势折线、等级分布、Top 模板柱图
2. **Alerts List**：表格（时间、类型、概率、状态），支持过滤
3. **Alert Detail**：模型输出 + 窗口统计 + 关键日志（高亮 ERROR） + LLM 卡片（summary + next_steps 清单 + 一键复制按钮）
4. **Replay Control**：选择数据集、速率 slider、启动/停止

---

## 11. Docker 化运行

Docker Compose 服务：
- kafka (+ zookeeper)
- spark-master/worker
- fastapi-backend
- mariadb
- vue-frontend

启动流程：
1. docker compose up -d
2. 初始化 DB 表 + 创建 Kafka topic
3. 离线训练生成 model.pkl（挂载卷）
4. 启动回放 → 看板观察告警 → 点击详情看 LLM 建议

---

## 12. 评测方案

- 离线：Accuracy、F1、Confusion Matrix
- 在线：告警延迟（<5s）、吞吐（不同速率下无 lag）、定性（Top 模板是否对应故障特征、LLM 建议是否合理）

---

## 13. 演示脚本（答辩流程）

1. 打开 Overview（正常无告警）
2. 启动 sample.log 回放（200 lines/s）
3. 出现告警 → 列表刷新
4. 点击详情：展示模型分类 + 证据统计 + LLM 排障清单
5. 强调“小模型快速检测 + 大模型精准解释”协同
6. 切换速率/数据集，展示稳定性

---

## 14. 实施阶段拆解（建议顺序）

**阶段1（2-3天）**：Kafka + Replayer + Spark 基本解析 → features topic 打通  
**阶段2（2天）**：离线训练模型 + 特征向量  
**阶段3（3天）**：FastAPI 推理 + 告警落库 + WebSocket 推送  
**阶段4（2天）**：LLM 接入 + 结构化输出  
**阶段5（3天）**：Vue 看板（先列表 + 详情，再图表）  
**阶段6（1-2天）**：Docker Compose + 联调 + 报告

这个合并版在保持工程完整性和课程技术覆盖的同时，难度大幅降低（预计 10-14 天可出完整 demo），答辩亮点突出（闭环 AIOps + 大小模型协同 + 实时流处理），非常适合拿高分。

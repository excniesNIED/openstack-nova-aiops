# 项目 Spec：基于 OpenStack Logs 的 AIOps 智能运维监控与故障诊断平台（无RAG版）

## 0. 一句话定义

用 OpenStack 日志构建一个“小型生产级”AIOps 演示系统：**离线训练故障分类模型 + 在线流式特征提取与告警 + 前端可视化看板**，实现从日志到告警闭环。

------

## 1. 项目目标与范围

### 1.1 目标（你要向老师证明的能力）

1. **大数据链路完整**：Kafka → Spark Streaming → HDFS/Hive + HBase → FastAPI → 前端看板
2. **AI 能力可量化**：用监督学习对日志窗口进行故障分类，输出 Macro-F1 / 混淆矩阵
3. **运维场景合理**：支持“日志回放模拟实时流”、告警去重/抑制、告警证据可追溯（能点开看到上下文日志）

### 1.2 范围（本版明确不做）

- 不做 RAG/向量库/检索增强
- 不做“自由聊天式运维助手”
- 不做复杂多租户权限体系（只做基础鉴权可选）
- 不追求 100% 模型准确率，追求“链路跑通 + 指标可解释 + 可演示”

------

## 2. 数据集与标签策略

### 2.1 数据来源

- 使用 `openstack-logs` 仓库内 OpenStack 日志文件（normal / fault1 / fault2 / fault3 / sample），其中：
  - **训练数据**：normal + fault1 + fault2 + fault3
  - **在线演示回放**：sample（混合/未知片段，用于触发告警并展示链路）

### 2.2 标签定义（监督分类主线）

- `0 = normal`
- `1 = fault1`
- `2 = fault2`
- `3 = fault3`

> 如果 sample 没有逐行标签：在线阶段只做“告警展示”，离线指标在训练/验证集上完成即可（非常常见且可答辩）。

### 3.1 可运行产物

5. 推理与告警服务：消费 features，产出 alerts，并落库

## 4. 总体架构（建议画成一张图）

### 4.1 分层

- **数据接入层**：Replay → Kafka
- **实时计算层**：Spark Streaming（解析/模板化/窗口聚合）
- **存储层**：HDFS/Hive（离线证据仓库）+ HBase（在线快速上下文）+ MariaDB/SQLite（业务库）
- **服务层**：FastAPI（告警API/推理worker/回放控制）
- **展示层**：Vue + Astro + Charts

### 4.2 数据流（主链路）

1. Replay 读取日志文件 → 写入 `openstack.raw`
2. Spark Streaming 消费 raw → 解析字段 + 模板化 → 窗口聚合特征 → 写入
   - Kafka：`openstack.features`
   - HBase：recent logs / recent windows（可选但很加分）
   - Hive：落地 parsed/window（用于离线报表与证据追溯）
3. Inference Worker 消费 `openstack.features` → 模型推理 → 生成告警 → 写入
   - Kafka：`openstack.alerts`（可选，做异步解耦）
   - MariaDB：alerts 表（前端查询）
4. 前端查询 FastAPI：列表、详情、趋势图、回放控制

## 5. 数据与存储设计（工程感关键）

## 5.1 Kafka Topic 设计（至少3个）

### Topic A：`openstack.raw`

- **用途**：原始日志入口（模拟实时）
- key：`entity_key`（优先 instance_id，其次 request_id，否则 global）
- value（JSON）：
  - `dataset_id`：normal / fault1 / fault2 / fault3 / sample
  - `ingest_ts`：回放写入时间（毫秒）
  - `raw_line`：原始日志行

### Topic B：`openstack.features`

- **用途**：窗口聚合后的特征（给推理服务消费）
- value（JSON）：
  - `window_start`, `window_end`
  - `entity_key`
  - `counts`：模板计数（稀疏字典：{template_id: count}）
  - `error_cnt`, `warn_cnt`, `total_cnt`, `error_ratio`
  - `top_templates`：TopK 模板ID列表
  - `dataset_id`

### Topic C：`openstack.alerts`

- **用途**：告警事件流（前端可订阅 / 或仅用于解耦）
- value（JSON）：
  - `alert_id`, `alert_ts`, `severity`
  - `entity_key`, `dataset_id`
  - `pred_class`, `score`
  - `evidence`：top_templates + log_refs（指向HBase/Hive）

------

## 5.2 Hive/HDFS（离线证据仓库）

> 离线“可追溯”是答辩最容易加分的点：告警不是凭空来的，能回到 Hive 查证据。

建议三层表：

### ODS：`ods_openstack_raw`

- 分区：`dt=YYYY-MM-DD`，`dataset_id`
- 字段：`ingest_ts`, `raw_line`

### DWD：`dwd_openstack_parsed`

- 分区：`dt`, `dataset_id`
- 字段（统一schema）：
  - `event_ts`（若原日志有就解析，否则用 ingest_ts）
  - `level`（INFO/WARN/ERROR）
  - `component`（如 nova-compute）
  - `host`（可选）
  - `instance_id` / `request_id`（能抽则抽）
  - `message`（清洗后的消息）
  - `template_id`（模板编号）
  - `template_text`（可选）
  - `raw_line`

### DWS：`dws_openstack_window`

- 分区：`dt`, `dataset_id`
- 字段：
  - `window_start`, `window_end`, `entity_key`
  - `counts`（可用 map<string,int> 或 json string）
  - `error_cnt`, `warn_cnt`, `total_cnt`, `error_ratio`
  - `label`（仅训练数据有：0/1/2/3）

------

## 5.3 HBase（在线秒开详情）

> 目的：前端点开告警详情时，不扫 Hive。

建议两张列族表：

1. `recent_logs`

- rowkey：`entity_key#reverse_ts`
- 列：`event_ts, level, component, template_id, message, raw_line, dataset_id`

1. `recent_windows`

- rowkey：`entity_key#window_end`
- 列：`top_templates, error_ratio, counts, dataset_id`

------

## 5.4 MariaDB/SQLite（业务库）

### `models`

- `model_version` (PK)
- `created_at`
- `algo`（logreg/rf/mlp）
- `window_size_sec`, `slide_sec`, `topk_templates`
- `metrics_json`（Macro-F1、confusion等）
- `is_active`（当前在线使用版本）

### `alerts`

- `alert_id` (PK)
- `alert_ts`
- `dataset_id`
- `entity_key`
- `severity`（P1/P2/P3）
- `model_version`
- `pred_class`（0~3）
- `score`（概率或置信度）
- `status`（new/acked/closed）
- `evidence_json`（top_templates + log_refs）

## 6. 日志解析与模板化 Spec（系统成败关键）

### 6.1 为什么要模板化

原始日志包含大量变量（UUID、IP、数字、路径），直接文本建模噪声大。模板化把日志变成“事件序列/模板序列”，更利于泛化与解释。

### 6.2 解析输出字段（统一 schema）

- `event_ts`
- `level`
- `component`
- `instance_id` / `request_id`
- `message_clean`
- `template_id`（模板编号）
- `raw_line`

### 6.3 模板化策略（简化但可用）

**不实现复杂算法也能拿分的做法：**

1. 正则归一化：
   - UUID → `<UUID>`
   - IP → `<IP>`
   - 数字 → `<NUM>`
   - 路径 → `<PATH>`
2. 模板生成：
   - `template_text = normalized_message`
   - `template_id = hash(template_text)`（或递增ID）
3. 训练阶段建立 `template_id ↔ template_text` 映射（持久化）
4. 在线阶段复用同一归一化规则，保证一致性

## 7. 特征工程与窗口策略

### 7.1 窗口定义（默认）

- window_size：60s（可配置 30/60/120）
- slide：10s（滑动窗口更容易触发及时告警）
- entity_key：
  - 优先 `instance_id`
  - 其次 `request_id`
  - 否则 `global`

### 7.2 特征（窗口内）

- 模板计数向量：`counts[template_id]`
- `error_cnt`, `warn_cnt`, `total_cnt`, `error_ratio`
- TopK 模板：`top_templates`
- 可选增强：Top component、unique template count

------

## 8. 模型训练与版本管理

### 8.1 训练数据构建（离线批处理）

1. 原始日志导入 HDFS/Hive：`ods_openstack_raw`
2. Spark Batch：
   - 解析 + 模板化 → `dwd_openstack_parsed`
   - 窗口聚合 → `dws_openstack_window`（带 label）
3. 导出训练集（Parquet/CSV）供 sklearn/PyTorch

### 8.2 模型选择（主线推荐）

- **首选：sklearn Logistic Regression / RandomForest**
  - 优点：实现快、效果稳定、可解释（特征权重/重要性）
- 可选：PyTorch MLP（加分，但不是必须）

### 8.3 输出与版本

每次训练产出 `model_version`，包括：

- 模型文件：`model.joblib` 或 `model.pt`
- 模板映射：`templates.json`
- 特征配置：窗口大小、topK、vectorizer 字典等
- 指标：Accuracy、Macro-F1、混淆矩阵（存为 json/png）
- 写入 `models` 表；模型文件存 HDFS 或挂载卷

------

## 9. 在线流式处理（Spark Streaming）

### 9.1 输入

- Kafka `openstack.raw`

### 9.2 处理逻辑

1. 解析字段 + 清洗 + 模板化
2. 按 `entity_key` 做滑动窗口聚合
3. 生成 feature JSON
4. 输出：
   - Kafka：`openstack.features`
   - HBase：recent_logs / recent_windows（可选）
   - Hive：追加写入 dwd/dws（可选但加分）

### 9.3 可靠性要求（作业级别足够）

- 至少保证不崩、可重启
- 支持配置回放速率下不丢消息（用 Kafka lag 展示）

------

## 10. 后端服务 Spec（FastAPI）

### 10.1 组件拆分

1. **Inference Worker（常驻后台）**
   - 消费 `openstack.features`
   - 载入 active `model_version`
   - 推理得到 `pred_class + score`
   - 告警策略：非 normal 或 score 超阈值
   - 告警抑制：同 entity_key 同类告警 cooldown 30s（避免刷屏）
   - 写入 DB（alerts），可选写入 Kafka `openstack.alerts`
2. **HTTP API（给前端）**
   - 只做查询/控制，不承担重计算
3. **Replay Control（可选实现为后端调用脚本）**
   - 启动/停止回放器进程，设置速率、数据集

### 10.2 API 清单（建议）

- `GET /datasets`
  - 返回：[`normal`,`fault1`,`fault2`,`fault3`,`sample`]
- `POST /replay/start`
  - body：`{dataset_id, rate_lines_per_sec}`
- `POST /replay/stop`
- `GET /alerts`
  - query：time range / severity / dataset_id / pred_class / status
- `GET /alerts/{alert_id}`
  - 返回：告警详情 + evidence + 上下文日志（从 HBase 拉最近 N 条）
- `POST /alerts/{alert_id}/ack`
  - body：`{comment?}`（可选）
- `GET /metrics/overview`
  - 返回：近10分钟告警数、等级分布、Top模板等（前端总览用）

## 11. 前端看板 Spec（Vue + Astro + TS + Charts）

### 11.1 页面设计（至少4页）

1. **Overview 总览**
   - 回放状态（running/rate）
   - 告警趋势（折线）
   - 告警等级分布（饼/柱）
   - Top templates / Top components（表格/柱状）
2. **Alerts 告警列表**
   - 表格：时间、等级、类型、entity_key、score、状态
   - 过滤：数据集/等级/类型/时间范围
3. **Alert Detail 告警详情**
   - 模型输出：pred_class、score、model_version
   - 证据：top_templates、error_ratio、窗口统计
   - 上下文日志：最近 N 条日志（高亮 ERROR/WARN）
4. **Settings / Replay**
   - 选择 dataset（默认 sample）
   - 速率 slider（100/300/500 lines/s）
   - 窗口大小选择（30/60/120）

## 13. 评测方案（必须有指标）

### 13.1 离线评测（训练/验证集）

- Accuracy（可选）
- **Macro-F1（必做）**
- Confusion Matrix（必做）
- 可选：每类 Precision/Recall

### 13.2 在线评测（sample 回放）

- 告警延迟：`alert_ts - ingest_ts`
- 吞吐：不同回放速率下 Kafka lag、处理延迟是否可控
- 告警抑制效果：同一段异常是否被 cooldown 合并（对比开启/关闭）
- 解释性（定性）：Top templates + 上下文日志是否能“讲得通”

## 16. 风险与规避（写进报告很加分）

- **instance_id 抽不到**：entity_key 退化到 request_id / global，保证系统仍能跑
- **模板数爆炸**：对 template 做 topK 截断或 hash trick，保持特征维度可控
- **类别不平衡**：用 class_weight 或下采样/上采样；指标用 Macro-F1
- **重复告警刷屏**：cooldown 抑制 + status=acked/closed 流程
